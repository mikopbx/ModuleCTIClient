# Подзадача: периодическая синхронизация логов удалённых мессенджеров с VPS

**Статус:** спека к реализации (агент)
**Контекст:** offload мессенджеров на VPS (см. память `remote-messengers-vps-state`). Когда сервис вынесен на VPS, его демон пишет логи на VPS под `{base}/logs/<service>/`, а локально в `System::getLogDir()/ModuleCTIClient/<service>/` ничего не появляется. Поэтому встроенные механизмы анализа логов MikoPBX (System → Logs, REST `syslog_GetLogsList` / `GetLogFromFile`) их **не видят**.

## Цель
Периодически выкачивать логи вынесенных сервисов с VPS в локальный logDir **так, чтобы они анализировались штатными средствами MikoPBX** (System → Logs) без какой-либо доработки ядра.

Это работает «бесплатно»: `Core/src/PBXCoreREST/Lib/SysLogs/GetLogsListAction.php` сканирует `System::getLogDir()` **рекурсивно** (`scanDirRecursively`) и отдаёт каждый файл по относительному пути. Любой файл под `logDir/ModuleCTIClient/.../*.log` автоматически попадает в список и доступен на просмотр/скачивание — в т.ч. во вложенной подпапке.

## Принятые проектные решения
1. **Выкачка — инкрементальная по offset** (не полный pull). Экономия трафика через ssh-туннель.
2. **Размещение — отдельная папка сервиса с хостом:** `logDir/ModuleCTIClient/<service>-<host>/<file>`, где `<host>` — sanitized имя/IP удалённого VPS (из `remote_host`; оставить `[A-Za-z0-9._-]`, прочее → `_`). Это **структурно исключает пересечения** с живым локальным логом (`logDir/ModuleCTIClient/<service>/`) и сразу видно, с какого хоста лог. Файл всё равно виден в System → Logs (рекурсивный скан). Непрерывность истории при failback НЕ требуется — это отдельный архив VPS-периода. (Альтернатива «тот же путь, неотличимо» отклонена в пользу нулевого риска коллизии и видимого источника.)
3. **Гейт:** тянуть логи сервиса **только когда его routing side == remote** **и туннель connected**. Коллизия уже исключена отдельной папкой, но тянуть имеет смысл только пока VPS-демон реально пишет (т.е. сервис там). При нескольких хостах за время жизни — у каждого своя `<service>-<host>` папка.

## Раскладка путей (факты из кода)
- Локально: `System::getLogDir()` → `…/ModuleCTIClient/` → подпапки на сервис: константы `SERVICE_CHATS='chats'`, `SERVICE_TELEGRAM='tg'`, `SERVICE_MAX='max'` (см. `AmigoDaemons::__construct`, `$this->dirs['logDir']`).
- На VPS: `{base}/logs/<service>/` создаётся при провижининге (`AmigoDaemons.php` ~1176-1180; `$base = getRemoteBaseDir()`). Демоны на VPS пишут туда (`log_path` в их JSON-конфигах указывает на этот каталог).
- Мигрируемые сервисы: `MIGRATABLE_SERVICES = ['chats','tg','max']`.

## Транспорт (переиспользовать существующее)
- ssh-параметры/аргументы: `getRemoteSshParams()` + `buildSshArgs()` (как в mirror-пути). Туннель во владении monitord; воркер только тянет.
- Уже есть `scpPush()` и tar-over-ssh (`mirrorAreaSessionFiles` — remote `tar -cf -` → local `tar -xf -`). Для инкремента tar не подходит — нужен побайтовый хвост (см. ниже).

## Алгоритм (на каждый тик pull)
Состояние offset'ов: новый файл `spoolDir/remote_logs_state.json`, карта `"<service>/<filename>" => { "size": <int>, "head": "<hex sig>" }`. Атомарная запись (temp+rename + `fsyncOrFlush`), один писатель — воркер, лок не обязателен (но не мешает).

Для каждого `service` из `MIGRATABLE_SERVICES`:
1. **Гейт:** если side != remote (читать из `readRemoteState()` areas[].side, либо location из custom_config) **или** туннель не connected (`isRemoteTunnelConnected()`) → пропустить сервис.
2. **Листинг remote** одним ssh-вызовом — портируемый shell (VPS может быть busybox, без GNU `find -printf`):
   ```sh
   for f in "{base}/logs/<service>"/*.log; do
     [ -f "$f" ] || continue
     printf '%s\t%s\n' "$(wc -c < "$f")" "$f"
   done
   ```
   Берём **только активные `*.log`**, НЕ ротированные `*.log.N` (их содержимое мы уже инкрементально вытянули в локальный активный файл; повторно тянуть архивы = дубль).
3. Для каждого remote-файла `size_new`, локальная цель `logDir/ModuleCTIClient/<service>-<host>/<basename>` (создать каталог через `Util::mwMkdir`):
   - **новый файл** (нет в state) → тянуть целиком: `tail -c +1 | head -c <size_new>`, записать локально, `offset=size_new`.
   - **дописан** (`size_new > old`) → тянуть ровно хвост `[old, size_new)`:
     ```sh
     tail -c +$((old+1)) -- "$f" | head -c $((size_new-old))
     ```
     **append** к локальному файлу, `offset=size_new`. `head -c` ограничивает ровно дельтой, чтобы при росте файла во время передачи offset оставался точным (нет дублей в след. тик).
     **Портируемость:** `tail -c +N` (старт с N-го байта) — GNU-расширение. На provisioned-VPS (обычно Debian/Ubuntu → GNU coreutils) есть. Если VPS на busybox без `+N` — фолбэк `dd if="$f" bs=1 skip=$old count=$((size_new-old))` (медленнее на больших offset, но переносимо). Агент: проверить, что шлёт VPS-образ.
   - **ротация / truncate** (`size_new < old`, либо изменилась `head`-сигнатура при равном размере) → начать с 0: тянуть весь текущий `*.log` и **append** к локальному (новое содержимое после copytruncate / нового файла — это реальные новые строки, продолжаем историю), `offset=size_new`.
4. **head-сигнатура** (опц., но желательно для надёжности): хранить хэш первых ~64 байт файла, чтобы ловить ротацию create+rename, где `size_new` может случайно совпасть. Считать дёшево: `head -c 64 "$f" | md5sum` в том же листинг-вызове, либо отдельным батчем.

## Ротация локального файла
Локальный append-файл `<service>.log` растёт неограниченно. Существующая чистка в `AmigoDaemons` (`find logDir -name '*.log.[0-9]*' -mtime +7`) убирает только ротированные, но не крутит активный `.log`. **Требуется:** при превышении порога (напр. конфигурируемый размер, дефолт ~10 МБ) ротировать локальный pulled `.log` → `.log.1` (и т.д.), чтобы существующая 7-дневная чистка их подхватывала. Не ломать логику локального демона на тех же путях.

## Имена файлов
Используем remote-basename как есть внутри `<service>-<host>/`. Паритет с локальным именем теперь НЕ критичен (отдельная папка, истории не сливаются), так что сверять local vs VPS имя не обязательно — но валидировать basename (без `/` и `..`) обязательно.

## Опционально: лог самого VPS-monitord
`{base}/logs/<SERVICE_MONITOR>/` и `{base}/logs/monitord.out` на VPS — ценны для диагностики самого offload. Можно тянуть тем же механизмом (гейт — «хотя бы один сервис remote / туннель up», не per-service side, т.к. monitord не в `MIGRATABLE_SERVICES`). Класть в `logDir/ModuleCTIClient/monitor-<host>/` (та же схема `<service>-<host>`) — коллизии с локальным monitord-логом нет. Решить с заказчиком, нужно ли в первой итерации.

## Точки интеграции
- Новый публичный метод `AmigoDaemons::pullRemoteLogsToLocal(): void`.
- Вызов из `WorkerRemoteTunnel` главного цикла на **отдельной, более редкой** каденции, чем session-mirror (логи менее срочны): троттлинг ~60 c (напр. таймштамп последнего pull в state-файле, либо счётчик тиков). Сам цикл уже периодический.
- Ранний выход, если offload не сконфигурирован / нет ни одного remote-сервиса (как делает heal/mirror).

## Требования к качеству
- **PHP 7.4 И 8.4**: без `str_*`/`match`/`?->`/enum/readonly/именованных аргументов; nullable → typed string через `?? ''`/`(string)`; `fsync` через `function_exists` (есть `fsyncOrFlush`).
- **escapeshellarg** на ВСЕ интерполируемые значения (base, service, имена файлов из remote-листинга). Валидировать, что basename не содержит `/` и `..` (защита от вырывания за пределы logs-каталога).
- Ошибки ssh/частичные передачи: пропустить тик, **не сбрасывать** offset'ы (кроме явной ротации). Атомарная запись локальных файлов где возможно (для append — открыть `a`, писать дельту; при сбое offset не двигать).
- Не держать ssh-сессию дольше тика; reuse `ConnectTimeout`/`BatchMode` из `buildSshArgs`.
- Не мешать существующему session-mirror и reconcile; отдельный state-файл.
- Прунить из state-файла записи об исчезнувших remote-файлах (иначе карта растёт без конца).

## Тест-сценарии (ручные/стендовые)
1. Сервис на VPS, лог растёт → локальный файл инкрементально догоняет, без дублей и пропусков (diff с remote `wc -c`).
2. copytruncate на VPS → локально видим новые строки, история не теряется.
3. create+rename ротация → детект по head-сигнатуре, без дублей.
4. failback на локальный → pull прекращается для сервиса; папка `<service>-<host>/` остаётся архивом VPS-периода, локальный демон пишет в свою `<service>/`, коллизии нет.
5. VPS недоступен/туннель down → тик пропускается, offset'ы целы, на восстановлении догоняет.
6. Локальный файл превысил порог → ротация в `.log.1`, 7-дневная чистка подхватывает.
7. busybox-VPS (нет GNU find/stat) → листинг через `wc -c`/`tail -c`/`head -c` работает.

## Вне зоны (отдельно)
- Go-сторона: убедиться, что remote-демоны действительно пишут в `{base}/logs/<service>/` с предсказуемыми именами файлов (см. отдельную задачу-память `go-contract-followups-suppressed-row-and-max-session` про контракт Go).
