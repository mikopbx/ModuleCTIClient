# Вынос мессенджеров на VPS — технический спек реализации (модуль с нуля)

**Аудитория:** агент/разработчик, который пишет **новый модуль с новыми бинарниками** и реализует вынос
мессенджеров (WhatsApp/Telegram/MAX) на внешний VPS. Это самодостаточный технический спек: что построить,
как именно, какие форматы конфигов и контракты соблюсти, и **чек-лист приёмки** в конце.

Документ описывает **целевую реализацию**, а не историю. Конкретные имена функций/файлов даны как ориентиры —
в новой архитектуре они могут отличаться, но **контракты и инварианты соблюдать обязательно**.

---

## 0. Что строим (в двух предложениях)

Демоны мессенджеров переносятся с PBX на VPS в «чистой» (без DPI) локации. PBX остаётся «мозгом» (NATS,
лицензия, супервизор, маршрутизация, 1С), VPS гоняет только демоны; связь — один исходящий SSH-туннель,
которым владеет супервизор (monitord) на PBX.

---

## 1. Карта компонентов

| Компонент | Где | Роль |
|---|---|---|
| `gnatsd-cti` | **PBX** | NATS-шина (`:4222`) + HTTP-шлюз/лицензия (`:8222`). Единственная точка входа 1С. Не переносится. |
| `monitord` (local) | **PBX** | Супервизор всего стека + маршрутизатор каналов + **владелец SSH-туннеля**. `manager.api` на `:8225`. |
| `amid / crmd / authd / proxyd / speechd` | **PBX** | AMI, 1С-CRM, авторизация, прокси, речь. Не переносятся. |
| `chatsd / tgd / maxd` | **PBX или VPS** | Демоны мессенджеров. Уезжают на VPS поканально-посервисно по тумблеру. |
| `monitord` (remote) | **VPS** | Тонкий супервизор: запускает/перезапускает демоны на VPS, отдаёт их статус, проксирует `/chats/*`. `daemons=[]`, bind только loopback. |
| Воркер оркестрации (PHP) | **PBX** | Провижининг VPS, запуск remote-monitord, миграция/зеркало сессий, pull логов, авто-failback. **Туннель НЕ держит.** |

**Главный принцип разделения:** **роутинг — в супервизоре (Go), оркестрация — в модуле (PHP).** Модуль доставляет
намерение в супервизор **только** через его конфиг (`remote_services`, `suppressed`) + вызов `POST /manager.api/reconcile`.
`custom_config.json` (реестр каналов) пишет **только супервизор**. Двух писателей в `custom_config` быть не должно.

## 2. Несущие допущения о бинарниках — ПРОВЕРИТЬ ПЕРВЫМ

Вся архитектура держится на 6 свойствах демонов. **Перед написанием кода убедитесь, что новые бинарники им
удовлетворяют** (или заложите эти свойства при их разработке). Рядом — что сломается, если свойство отсутствует.

1. **Демон — NATS-КЛИЕНТ:** сам дозванивается до `mq.host:port` из своего конфига; никто к нему по NATS не
   коннектится. → reverse-форвард `-R 4222` (на VPS `localhost:4222` → gnatsd PBX) — этого достаточно.
   *Нарушено (демон слушает входящие/он сервер)* → reverse-форвард не работает, нужна другая топология.

2. **Единственная сетевая «прошивка» демона — лицензия `http://127.0.0.1:8222`** (feature **42**, одна на все три).
   → закрывается reverse-форвардом `-R 8222`. *Нарушено (демон ходит ещё куда-то по фиксированному адресу)* →
   нужен ещё форвард/конфиг; туннель из 3 форвардов не покроет.

3. **Health демонов — NATS-пинг по subject** `daemon.<svc>.<area>.ping/.status`. → статус location-transparent
   (супервизору неважно, где физически демон). *Нарушено (health по локальному PID/порту)* → remote-демон всегда «мёртв».

4. **Файл сессии несёт всю авторизацию и переживает перенос между хостами и смену IP/гео без ре-авторизации.**
   → миграция = копирование файлов. **Это премиса всей фичи.** *Нарушено (сессия привязана к IP/устройству)* →
   миграция без ре-пайринга невозможна, переосмысливать дизайн.

5. **1С ходит ТОЛЬКО в `gnatsd:8222`**, весь её data-plane — HTTP `/chats/*`. Путь:
   `1С → gnatsd:8222 → monitord:8225 → демон:822X`. NATS-`messenger.v1.event` — фид Electron-клиента, для 1С не транспорт.

6. **Демоны лицензионно-зависимы (feature 42 через gnatsd PBX):** standalone на VPS не работают (`403`). →
   всегда нужен живой туннель к лицензированному PBX. By design — учитывать в тестах (нельзя тестить демон на VPS без туннеля).

Дополнительно проверить: **демон FATAL без NATS на старте** (→ туннель поднимать ДО демонов; супервизор и так
респавнит) и **умирает ли демон вместе со своим monitord** (важно для фенсинга, §9).

## 3. SSH-туннель

**Владелец — `monitord` на PBX** (встроенный SSH-клиент с авто-реконнектом и keepalive). Модуль рендерит блок
`ssh_tunnel` в `monitord.json`; супервизор читает его на старте и держит соединение. Отдельного процесса
`ssh -N` нет. При любой регенерации конфига блок пере-рендерится — туннель не теряется.

**Три фиксированных форварда** (их число НЕ зависит от количества каналов):

| Форвард | Направление | Назначение |
|---|---|---|
| `-R 127.0.0.1:4222 → PBX:4222` | reverse: VPS-loopback → PBX | NATS-шина |
| `-R 127.0.0.1:8222 → PBX:8222` | reverse: VPS-loopback → PBX | HTTP-шлюз + лицензия (feature 42) |
| `-L 127.0.0.1:8226 → VPS:8225` | local: PBX → VPS | `manager.api` удалённого monitord (прокси `/chats/*`, сбор статуса) |

Динамические порты каналов на VPS (`8228, 8229, …`) проксирует **сам remote-monitord** — per-port форварды не нужны.

**Параметры:** транспорт SSH на порту `remote_ssh_port` (дефолт `22`), аутентификация приватным ключом,
`keepalive_sec=15`, `StrictHostKeyChecking` с pinned known_hosts (TOFU, приоритет ed25519).

**owner-lock (фенс single-owner):** PBX-monitord держит на VPS lock с TTL (`owner_lock_path`,
`owner_lock_ttl_sec=120`, heartbeat = `keepalive_sec`). Партиция → heartbeat прекращается → lock протухает.
Это фундамент безопасного failback (§9) и защита от двух конкурирующих туннелей на одни порты.

**Эндпоинт статуса:** `GET http://127.0.0.1:8225/manager.api/tunnel/status` →
```json
{ "result": { "configured": true, "connected": true, "state": "connected",
              "last_ok_ts": 1781677831, "last_error": "", "attempts": 1 } }
```

### Формат блока `ssh_tunnel` в `monitord.json` (PBX)
```jsonc
"ssh_tunnel": {
  "host": "<remote_host>", "port": "22", "login": "<login>",
  "key_path": "<spool>/remote_id", "known_hosts_path": "<spool>/remote_known_hosts",
  "keepalive_sec": 15,
  "owner_id": "<стабильный non-secret id>", "owner_label": "<метка>",
  "owner_lock_path": "<path на VPS>", "owner_lock_ttl_sec": 120,
  "forwards": [
    { "listen_addr": "127.0.0.1:4222", "target_addr": "127.0.0.1:4222" },
    { "listen_addr": "127.0.0.1:8222", "target_addr": "127.0.0.1:8222" }
  ],
  "local_forwards": [
    { "listen_addr": "127.0.0.1:8226", "target_addr": "127.0.0.1:8225" }
  ]
}
```

## 4. Справочник портов

| Порт | Хост | Доступность | Что это |
|---|---|---|---|
| `22` | VPS | вход SSH только от PBX | транспорт туннеля (`remote_ssh_port`) |
| `4222` | PBX | loopback + reverse-форвард | NATS-шина |
| `8222` | PBX | открыт в firewall (вход 1С) + reverse-форвард | HTTP-шлюз gnatsd + лицензия. **Единственный вход 1С** |
| `8225` | PBX и VPS | только loopback | `manager.api` супервизора. На VPS bind `127.0.0.1` (наружу не торчит) |
| `8226` | PBX | только loopback | local-форвард на `:8225` remote-monitord. LISTEN на 8226 = туннель сконфигурирован |
| `8228+` | VPS | внутри VPS | динамические порты каналов (проксирует remote-monitord) |
| `8224 / 8227` | PBX | loopback | crmd / речь (stt) — за шлюзом `:8222`, не переносятся |

## 5. Генерация конфигов

Все JSON генерируются в каталог конфигов PBX (`confDir`, напр. `/etc/custom_modules/ModuleCTIClient/`);
remote-варианты стейджатся в `{spool}/remote/` и заливаются на VPS при провижининге.

### 5.1 `monitord.json` (local, PBX)
- `mq: { host: "127.0.0.1", port: "4222" }`
- **полный** список `daemons` (gnatsd-cti, amid, crmd, authd, proxyd, speechd, локальные мессенджеры) — супервизор
  ведёт весь стек;
- при непустом `getRemoteServices()`: `"remote_monitor": "127.0.0.1:8226"` + `"remote_services": ["chats", …]`;
- блок `ssh_tunnel` (см. §3);
- (для self-fence, §9) durable `suppressed: [...]` — сервисы, которые надо заглушить.

### 5.2 `monitord.json` (remote, VPS)
```jsonc
{
  "mq": { "host": "127.0.0.1", "port": "4222" },
  "bind_address": "127.0.0.1",          // manager.api только через туннель
  "binary_dir":   "{base}/bin",
  "settings_dir": "{base}/conf",
  "work_dir":     "{base}/spool",
  "log_path":     "{base}/logs/monitord",
  "period": 30,
  "daemons": []                          // каналы добавляются динамически через manager.api
}
```
`{base}` = `remote_bin_dir` (дефолт `/opt/mikopbx-cti`). Пути — **абсолютные** (относительный `-c` → fatal).
На VPS НЕТ gnatsd/amid/crmd → `daemons=[]` корректно (в отличие от PBX, где `daemons=[]` уронит gnatsd).

### 5.3 Конфиги демонов (`chats.json` / `tg.json` / `max.json`)
**Общие на все area сервиса** (area задаётся флагом `-a`, порт — `-p`). Ключевое:
`mq.host=127.0.0.1`, `port=4222`; `database.path` → `{base}/db/<svc>`; `log_path` → `{base}/logs/<svc>`;
корректные `log_level`; `proxy_address` (chats/max) и условный `mt_proxy` (tg). Remote-вариант = локальный с
путями VPS и `mq.host=127.0.0.1` (резолвится через туннель).

### 5.4 `getRemoteServices()`
Подмножество `['chats','tg','max']` по тумблерам. **Пусто при пустом `remote_host`** → безопасный дефолт «всё локально».
Для провижининга/инфраструктуры использовать **`getInfraServices()`** (area уже remote ИЛИ идёт миграция), а НЕ
`getRemoteServices()` — иначе слив последнего сервиса остановит провижининг до завершения миграции назад.

## 6. Контрольный путь и маршрутизация

**UI:** 3 тумблера (`remote_whatsapp`/`remote_telegram`/`remote_max`) + SSH-поля (`remote_host`,
`remote_ssh_port`, `remote_ssh_login`, `remote_ssh_key`, `remote_bin_dir`).

**Метка размещения — по area, не по тумблеру.** Тумблер = политика сервиса (дефолт для новых каналов + цель
миграции). Реальный роутинг идёт по полю `location ∈ {local, remote}` каждой area в `custom_config`. Иначе щелчок
тумблера сольёт трафик всех каналов сервиса на неготовый супервизор до миграции.

**Реестр каналов `custom_config.json`** (пишет только супервизор), per-area:
`{ name, area, port, location, subject, suppressed }`. Переживает ребут (супервизор респавнит каналы на старте).

**Маршрутизация в супервизоре:**
- `POST /manager.api/daemons {name, area}` от 1С: если `name ∈ remote_services` → переслать на `remote_monitor`,
  записать локальный stub `location=remote` (subject есть, локально НЕ спавнится); иначе спавнить локально.
- `DELETE /manager.api/daemons/{area}`: `remote` → форвард на `remote_monitor` ПЕРЕД удалением stub.
- `GET /manager.api/status`: статусы каналов сливаются автоматически по NATS (location-transparent). **Каждая
  строка обязана содержать `area` + `state`** (включая `stopped`/`suppressed`/`error` для killed/suppressed) —
  иначе оркестратор не сможет детектить «down» (см. §7 `bothSidesDown`).
- Прокси `/chats/*` по заголовку `Area`: `remote` → реверс-прокси на `remote_monitor`. **Контракт прокси:**
  ставить URL на `:8226` **И явно Host = `127.0.0.1:8225`** (это разные поля!) — иначе на VPS не сработает
  подстановка порта и будет dial в `:8226`.
- **Инвариант:** недоступность remote НИКОГДА не блокирует локальные пути. Все обращения к `remote_monitor` —
  с таймаутом и ленивые; старт супервизора НЕ зависит от доступности remote.

**Реконсиляция:** `POST /manager.api/reconcile` запускает проход, который сверяет `location` каждого канала с
`remote_services`/`suppressed` и релоцирует (in-place, в одной горутине-цикле, без гонки с супервизией).
Модуль доставляет намерение через `monitord.json`, затем дёргает `/reconcile`. **Модуль не пишет `custom_config`
и не делает per-area add/delete сам.**

**Триггер применения настроек:** изменение модели (Phalcon `afterSave`) → событие → регенерация конфигов +
реконсиляция. ⚠️ Прямой `sqlite UPDATE` НЕ триггерит `afterSave`; UI-Save без реального диффа поля — тоже.
Тестировать тумблеры только реальным 0↔1 через UI/модель.

## 7. Миграция состояния (конечный автомат)

Срабатывает при флипе тумблера (local↔remote). Цель: перенести сессию и переключить `location` **без потери
авторизации и без одновременного запуска канала на двух сторонах**.

```
STEP 1  SUPPRESS  — заглушить сервис/area с ОБЕИХ сторон (флаг suppressed/migrating)
STEP 2  COPY      — tar-over-ssh нужной стороне: temp-файл → sha256-сверка → atomic rename
STEP 3  FLIP+RESUME — записать новый location (атомарно, в custom_config), снять suppress
STEP 4  CONFIRM   — дождаться health приёмника; иначе ROLLBACK на источник
        FAIL-PARK — при мёртвом VPS: cool-down, источник цел, без double-run
```

**Инварианты (нарушение = потеря сессии или дубль):**
- Один канал **никогда** не запущен на обеих сторонах. Глушение — через `suppressed` (супервизор skip+kill в
  цикле супервизии; НЕ изобретать отдельный stop-путь, иначе обычная супервизия респаунит убитый демон).
- Флип `location` пишется **атомарно** ДО любого рестарта. Релокация транзакционна (no-double-run при любом
  отказе forward-вызова).
- Источник держим живым/целым до подтверждённого health приёмника. Флип `side` — только после успешной копии.

**Mixed per-area:** старые area могут быть `local`, новые — `remote`. Истина — `custom_config` (read-only для
модуля). Копируем только файлы `<area>-*` нужных area; гейт — per-service.

**`remote_state.json`** (маркер оркестратора, в `{spool}`, под `flock` + atomic write):
- per-area: `{ side: local|remote, last_sync_ts, health }`
- per-service: `{ migrating, resuming, parked, fail_count, last_error }`
- Инвариант курсора: `suppressed ⟺ migrating && !resuming`.

**`bothSidesDown` / detect-down:** оркестратор решает «обе стороны мертвы» по `/manager.api/status`. Зависит от
того, что супервизор отдаёт строку с `area`+`state` даже для killed/suppressed демона. Без этого детект ложно
вернёт «не down» и suppressed-демон зависнет заглушённым. **Главный cross-stage контракт — заложить в супервизор.**

> При реализации автомата проработать отдельно: crash-safety на каждом шаге (что происходит при падении PBX/VPS
> между STEP-ами), транзакционность forward-вызовов (отказ forward не должен оставлять оба конца живыми) и
> deadlock-freedom (forward-HTTP под таймаутом, вне общего лока реестра каналов).

## 8. Сессии, бинарники, логи

### 8.1 Файлы сессий
| Сервис | Файл авторизации | Каталог |
|---|---|---|
| WhatsApp | `<area>-whatsappSession.db` (SQLite) | `{base}/db/chats/` |
| Telegram | `<area>-tgSession.json` | `{base}/db/tg/` |
| MAX | `<area>-max_session.json` | `{base}/db/max/` |

`cache.db` — волатильный кэш (несём при миграции, но не критичен). **Имена файлов новых бинарников — проверить и
при необходимости обновить в коде.** Копировать сессию только при **остановленном** демоне (sqlite/bolt в покое;
SIGKILL → crash-recovery/WAL-replay, не clean).

### 8.2 Тёплое зеркало
Пока канал на VPS, оркестратор периодически копирует сессию **remote→local**. Локальная копия всегда наготове →
потеря VPS ≠ потеря авторизации (закрывает невосстановимый кейс «аккаунт впервые авторизован на VPS, VPS умер»).

### 8.3 Транспорт миграции — tar-over-ssh, НЕ rsync
`rsync` есть не на всех VPS-образах (его требование подняло бы min_pbx_version). Используем
`cd $srcDir && tar -cf - <area>-*` | ssh | `tar -xf -` + **sha256-манифест** для контроля целостности.
⚠️ `tar -C $dir -cf - <glob>` раскрывает глоб в **home логин-шелла**, а не в `$dir` → используйте `cd $dir && tar`.
⚠️ Вложенный `ssh` без `-n` ест heredoc-stdin.

### 8.4 Провижининг + обновление бинарников
`provisionRemote()`: `ssh uname -m` (ждём x86_64) → `mkdir -p {base}/{bin,conf,db,logs,spool}` → залить бинарники
нужных сервисов + конфиги → `chmod +x`. Транспорт — `scp`/tar (не rsync).
- `{base}/bin/.version` — штамп версии модуля. Расхождение → **принудительный re-push** (без расхождения —
  сверка по размеру файла).
- Заливка **через temp + rename** (иначе перезапись работающего бинарника → `ETXTBSY`).
- После заливки — **bounce** затронутых демонов (рестарт remote-monitord или `pkill` дочерних), иначе на VPS
  останется старый код.
- Штамп пишется **только после полного успешного провижининга** → оборванный апгрейд повторится на ретрае.

### 8.5 Pull логов
Демоны на VPS пишут в `{base}/logs/<service>/` — локально невидимо. Оркестратор тянет **инкрементально по
offset** (только хвост файла) в `logDir/ModuleCTIClient/<service>-<host>/` (`<host>` = sanitized `remote_host`,
`[A-Za-z0-9._-]`). Гейт: `side==remote && tunnel connected`. Каденция реже зеркала (~60с). State offset'ов —
отдельный `{spool}/remote_logs_state.json` (atomic). Видно в System → Logs «бесплатно» (рекурсивный скан logDir).
Детект ротации/truncate — по `size_new < old` или смене head-сигнатуры. Портируемость busybox: листинг через
`wc -c`, хвост через `tail -c +N` (фолбэк `dd skip=`).

## 9. Failback и отказоустойчивость

- **Данные ≠ живость.** Данные держит зеркало (§8.2). Живость — owner-lock + VPS-self-fence.
- **adopt-local:** failback без pull — поднять локаль из **лежащей** копии (`location=local`, спавн), НЕ трактуя
  remote как источник. Намерение `adopt_local:[svc]` в `monitord.json` + `POST /reconcile`.
- **VPS-self-fence:** при протухшем owner-lock VPS-monitord гасит демоны (`suppressed`) → во время партиции VPS
  уходит вниз → PBX безопасно усыновляет локаль. `fence-grace > TTL` (иначе блип убивает WA-сессию).
- **Авто-failback:** порог `remote_failback_after_sec` (дефолт **7200с**). Downtime измеряется только
  durable-маркером `{spool}/remote_tunnel_down_since`: marker создаётся текущим временем при первом
  подтверждённом `configured=true, connected=false`, сохраняется через рестарты и удаляется при reconnect.
  `monitord.last_ok_ts` используется только для диагностики, поскольку отражает время установления текущей
  SSH-сессии, а не время последнего успешного keepalive. `N (failback) > grace > TTL`.
- ⚠️ **Не делать авто-фейловер при ЖИВОМ VPS** — две живые сессии = разлогин. Переход на локаль при доступном
  VPS — осознанный хэндовер (тумблер/миграция).

При недоступности VPS: локальная телефония/CRM/локальные мессенджеры не страдают; по remote-каналам пауза
отправки/приёма (data-plane по HTTP-туннелю); входящие не теряются навсегда (WhatsApp/TG держат бэклог, демон
вытянет после реконнекта).

## 10. Требования к коду

**Если модуль на PHP (ядро MikoPBX) — обе версии 7.4 и 8.4:**
- Запрещено: `str_starts_with/ends_with/contains`, `match`, `?->`, enum, readonly, fibers, именованные
  аргументы, intersection types (всё 8.0+). Использовать `strpos(...)===0`, `$s[0]==='{'`.
- Nullable → typed `string`: всегда `?? ''` / `(string)`.
- `fsync()` нет в 7.4 → `function_exists('fsync')` + `fflush`-фолбэк.
- `phpstan` после написания (требование `CLAUDE.md`).

**Безопасность shell/ssh (любой язык):**
- `escapeshellarg` (или эквивалент) на ВСЕ интерполируемые значения в ssh/tar/scp-командах.
- Валидировать basename файлов из remote-листинга (без `/` и `..`) — защита от вырывания за каталог.
- VPS: `bind_address=127.0.0.1` для manager.api; ужесточить `authorized_keys` (`restrict`/`permitopen`);
  ключ туннеля `chmod 600`.

## 11. Критические контракты (свести в одно место)

Эти 8 пунктов — интерфейс между супервизором и оркестратором. Нарушение любого ломает фичу молча:

1. `custom_config.json` пишет **только** супервизор; оркестратор — через `monitord.json` + `/reconcile`.
2. `GET /manager.api/status` отдаёт `area`+`state` для **каждой** строки, включая killed/suppressed.
3. Прокси `/chats/*` на remote: URL→`:8226` **И** Host→`127.0.0.1:8225`.
4. Local-monitord несёт **полный** `daemons` (супервизит gnatsd!); remote-monitord — `daemons=[]`.
5. Глушение канала — через `suppressed` (skip+kill в супервизии), не через сторонний stop.
6. Флип `location` — атомарный, ДО рестарта; релокация транзакционна (no-double-run).
7. Инфраструктура (туннель/remote_monitor) — по `getInfraServices()`, не по «живым» тумблерам.
8. Downtime для failback — по durable-маркеру, не по `last_ok_ts`.
